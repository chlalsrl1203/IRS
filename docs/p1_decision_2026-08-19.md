# P1 단계 판정 — §31 안티기능 등록부와의 충돌 처리 (2026-08-19)

사용자 지시: "스스로 합리적 판단. 이후 병합." P1 착수 전 계획서(§19 IMPLEMENTATION
ORDER)의 P1-01~05를 §31 ANTI-FEATURE REGISTER(`docs/irs_evolution_report_2026-08-16.md`)
와 대조해 판정한다. **새 코드는 작성하지 않는다** — 이번 판정 자체가 산출물이다.

## 왜 여기서 멈추고 판정부터 하는가

§31 등록부는 지어낸 목록이 아니라 2026-08-16 벤치마크 감사가 **근거와 함께**
등록한 것이다. P1-02(Agent/Skill Orchestration)와 P1-04(Portfolio/Risk)가 그
등록과 정면으로 겹친다. 등록된 근거를 다시 확인하지 않고 그냥 구현하면, 이
프로젝트가 반복 경계해온 "근거 없이 유지하던 걸 근거 없는 다른 것으로 대체"의
반대 방향 오류(근거 있게 안 만들던 걸 근거 없이 만듦)가 된다.

## 판정

| 단계 | Source | 판정 | 근거 |
|---|---|---|---|
| P1-01 Research DSL | myinvestpilot/ai-architecture | **DEFER** | 아래 ① |
| P1-02 Agent/Skill Orchestration | LangAlpha·DojoAgents·agno-agi·mattpocock | **REJECT** | 아래 ② |
| P1-03 Screening/Funnel | investment-funnel·stock-screener·TradingView-Screener·tvscreener | **DUPLICATE** | 아래 ③ |
| P1-04 Portfolio/Risk | PyPortfolioOpt·okama·NVIDIA blueprint | **REJECT** | 아래 ④ |
| P1-05 Intelligence/Monitoring | worldmonitor·investment-news | **DEFER** | 아래 ⑤ |

### ① P1-01 Research DSL — DEFER

"제약된 리서치 DSL·스키마 기반 계약·결정론적 실행"이 계획서의 캡처빌리티다.
IRS는 이미 `AnalysisInputs`(dataclass 필수 필드 강제)·`experiments/*.json`
(SHA-256 코어해시)·`Citation`/`Claim`(P0-12, 빈칸 거부)으로 **부분적으로 이
발상을 구현하고 있다.** 이걸 하나의 통합 DSL로 다시 감싸는 건 실증 필요가
없다 — 지금 형태로 막힌 분석이 하나도 없다. Simplicity First: "나중에 필요할
것 같아서"에 해당하면 넣지 않는다.

### ② P1-02 Agent/Skill Orchestration — REJECT

§31 표: *"멀티에이전트 리서치 오케스트레이션 — 현재 병목은 조율이 아니라
**입력의 근거 부재**(n·w). 에이전트를 늘려도 미검증 파라미터는 그대로다."*

이 판단은 지금도 유효하다. R-001 감사(STAGE 3)가 확인한 진짜 취약점은
`realistic_growth`·`model_choice`·`fcf0` 같은 **입력 가정의 근거 부족**이었고,
BRO 6.75%가 "과거 기록 답습"이라 원 근거를 복원할 수 없는 상태로 남아 있는
것도 같은 문제다. 에이전트를 여러 개 띄워 병렬 조사해도 그 입력을 검증된
근거로 바꿔주지 않는다. **등록을 뒤집을 새 증거가 없으므로 REJECT를 유지한다.**

### ③ P1-03 Screening/Funnel — DUPLICATE

`engine/screener.py`(380줄)가 이미: DRS 추정(`estimate_drs`) → 필요 FCF수익률
역산(`required_fcf_yield`/`implied_growth_from_fcf_yield`) → 4분류 체크리스트
(`Candidate`→`ScreenResult`, `screen()`) → 일괄 스크리닝(`screen_all`) → 표
출력(`format_table`)까지 전체 파이프라인을 담당한다. 25개 분석 스크립트가
반복 사용해왔고(2026-07-31~08-14 스크리닝 배치 다수), BSX false-rejection
사건으로 한계까지 실측·문서화됐다(`KNOWN_SCREENER_FALSE_REJECTIONS`).

계획서가 제안하는 "자연어 → 스크리닝 DSL → 스키마 검증 → 실행 → 후보 목록"
흐름은 이미 존재하는 것(코드 기반 필터 함수 체인)을 자연어 프론트엔드로
감싸는 일이다. TradingView-Screener·tvscreener의 필터 DSL·필드 발견 패턴은
**필요해지면**(예: 외부 사용자가 자연어로 스크리닝을 요청하는 경우) 참고할
가치가 있으나, 지금은 기존 함수 호출로 충분하다.

### ④ P1-04 Portfolio/Risk — REJECT

§31 표: *"상관행렬 기반 포트폴리오 최적화 — 수익률 시계열이 저장소에 없다.
없는 데이터로 최적화하면 정밀해 보이는 허구가 된다."*

이 판단도 지금 유효하다. `price_at_analysis`가 34종목 중 9건뿐이고(v3.48
EXP-001이 BLOCKED로 남은 바로 그 이유), 종목간 수익률 공분산을 계산할 시계열
자체가 없다. PyPortfolioOpt·okama·NVIDIA blueprint는 전부 공분산 행렬을
입력으로 요구하는데, 그 입력을 만드는 순간 **없는 데이터로 있는 척하는
행렬**이 된다. `scripts/build_buylist_2026_08_03.py`의 규칙기반 사이징
(버킷 목표비중 + quality_score 비례배분)이 "공분산 최적화가 아니라 투명한
규칙기반 배분"이라고 스스로 명시한 것도 같은 판단이다.

### ⑤ P1-05 Intelligence/Monitoring — DEFER

worldmonitor(cross-stream signal correlation)·investment-news(집계·중복제거·
이벤트추출)는 IRS의 현재 병목(입력 근거 부족)과 무관한 새 데이터 유형(뉴스
스트림)을 다룬다. `thesis_monitor.py`(반증조건 스캔)·`growth_scorecard.py`가
이미 "외부 신호와 대조"라는 기능을 좁은 범위에서 담당하고 있고, 뉴스 집계
파이프라인을 새로 세울 실증 필요가 아직 없다.

## 결론

P1은 **REJECT 2건 + DUPLICATE 1건 + DEFER 2건**으로 전부 판정되며, 새로
구현할 항목이 없다. §19 IMPLEMENTATION ORDER의 P0(P0-01~18)로 이번 통합
작업의 실질적 범위가 끝난다. P2(Portfolio/Risk 심화)·P3(Execution)는 P1-04
REJECT와 같은 이유로 더 강하게 배제된다(§31: "자동 매수/매도 실행 —
Gap은 연구 가설이지 검증된 alpha가 아니다").

## 재개 조건

- P1-02: 입력 근거 부족 문제가 실제로 해소된 뒤, 에이전트 조율 자체가 병목이
  되는 구체적 사례가 나오면.
- P1-04: `price_at_analysis`·수익률 시계열이 실질적으로 쌓여(예: 20종목 이상,
  6개월 이상) 공분산 계산이 "정밀해 보이는 허구"가 아니게 되면.
- P1-01·05: 지금 형태로 막힌 구체적 분석 사례가 생기면.
