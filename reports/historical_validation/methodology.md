# Methodology — Point-in-Time Historical Replay 시도와 그 한계

작성일: 2026-08-16

## 요청받은 것과 실제로 할 수 있는 것

요청된 워크플로(Phase 1-22)는 §2가 정의한 3-실험 구조를 전제한다:

```
EXPERIMENT A (역사적 원 결정) vs EXPERIMENT B (현재 IRS 재실행) vs EXPERIMENT C (실제 결과)
```

이 구조가 의미를 가지려면 **A/B가 동결된 후에 C가 공개**되어야 한다 — 즉 T0와
지금(관측 시점) 사이에 실제 시간이 흘러야 한다.

## §66 STOP CONDITION 공식 발동

Phase 1 저장소 포렌식으로 확인한 사실(전부 [CODE-VERIFIED]):

| 확인 항목 | 실측값 |
|---|---|
| 전체 137개 커밋의 시간 범위 | **2026-07-25 ~ 2026-08-16, 22일** |
| ledger 34종목의 분석일 범위 | 2026-07-25 ~ 2026-08-13 (최대 22일 전) |
| `price_at_analysis` 보유 종목 | 9/34 |
| `PIT_VALID` ledger | 0/34 (필드 자체 부재 — 아래 참고) |
| `predictions/` 디렉터리 파일 수 | 0 (디렉터리 자체 부재) |
| `thesis/` 디렉터리 파일 수 | 0 (디렉터리 자체 부재) |
| 가장 오래된 반증조건 검증(실제 T0→결과) | 9~11일 |

**이것은 데이터 품질 문제가 아니라 시간적 불가능성이다.** §33이 요구하는
1M/3M/6M/1Y/3Y/5Y 시장 아웃컴, §32의 다년 펀더멘털 아웃컴, §44-46의 개발/검증/
홀드아웃 분할, §21의 시간순 검증 — 전부 **아직 오지 않은 미래**를 전제로 한다.

§66이 명시한 STOP 조건 중 다음이 문자 그대로 해당한다:

> "historical source availability cannot be established"
> "sample size is insufficient"
> "holdout is no longer untouched" → **이 프로젝트엔 애초에 holdout이 존재한 적이 없다**

**따라서 Phase 5-10(진짜 T0 스냅샷 동결 → 미래 아웃컴 공개), Phase 44-46(개발/
검증/홀드아웃, 국면검증), Phase 21(최종 홀드아웃)은 지금 수행할 수 없다.**
데이터를 더 파거나 방법을 바꿔서 해결되는 문제가 아니다 — 실제 시간이
지나야 한다.

## ⚠️ 하지 않은 것 — "T0를 3주 전으로 재정의"의 유혹을 거부한다

분석일(2026-07-25~08-13)을 "T0"로 재정의하고 오늘(2026-08-16)을 "미래 아웃컴
공개 시점"으로 삼아 "3주짜리 historical replay"를 만들 수도 있었다. **하지
않았다.** 이유:

1. §33이 요구하는 최소 관측 단위(1M)에도 못 미친다 — 만들어봐야 통계적으로
   무의미한 숫자에 "historical validation"이라는 이름표만 붙이는 꼴이다.
2. §52가 명시적으로 경고한 함정("점수가 올랐다고 성공이 아니다")과 같은 유형 —
   "결과가 나왔다"는 사실 자체를 성과로 포장하는 것.
3. 이미 존재하는 진짜 데이터(growth_scorecard 11건 + falsification_scan 6건,
   총 17건)가 정확히 이 "3주짜리 관측"이다 — 새로 만들 필요 없이 **이미
   저장소에 있다.** 이걸 재발견하고 엄격하게 재분석하는 것이 옳은 접근이다.
