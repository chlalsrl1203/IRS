# IRS 체계적 디버깅

이 프로젝트가 실제로 반복해서 겪은 실패 패턴은 "결과를 먼저 안 뒤 그럴듯한
원인을 검증 없이 기록"하는 것이었다(WM/WCN FCF CAGR 오분석, MU FCF CAGR을
"82% 아티팩트"로 잘못 단정했다가 재확인, `broad_screen.yml`을 "SEC가 GitHub
Actions를 차단한다"고 의심했으나 실제론 후보 88%가 프레임워크 부적합이었던
사건). 이 스킬은 그 실패를 구조적으로 막는다.

## 4단계 - 순서를 건너뛰지 않는다

**1. 재현 - 실제로 실행해서 확인한다(추측 금지)**
- 에러 메시지·스택트레이스를 있는 그대로 읽는다. `ImportError`를
  "가드가 발동했다"로 잘못 집계한 사례(ALB 참조검증 스크립트)가 이
  프로젝트에 실제로 있었다 - 예외 타입을 좁혀서(`except ValueError` 등)
  진짜 발동 조건만 잡을 것.
- 최소 재현 케이스를 만든다. 34종목 전수를 다시 돌리기 전에 실패하는
  종목 1개로 먼저 좁힌다.

**2. 가설을 데이터로 검정한다 - 가설 하나당 확인 코드 하나**
- "아마 X 때문일 것이다"라고 적었으면, 그 즉시 X를 직접 확인하는 코드를
  써서 돌려본다. 확인 전에 CLAUDE.md나 커밋 메시지에 원인을 적지 않는다.
- IRS의 실제 실패 사례: "FY2025 10-K가 새로 나와서 그렇다"고 즉시
  설명했으나 제출일을 확인해보니 과거 분석일보다 5개월 이상 앞서 있었다
  (WM/WCN). "raw entries를 직접 열어보지 않고 요약값만 봐서" CDNS의
  회계연도 라벨 충돌을 놓칠 뻔한 사례도 있다.

**3. 도구 자체를 의심한다 - 결과가 극단적(0건/전건/불변)이면 특히**
- 이 프로젝트에서 반복 확인된 규칙: **측정 결과가 "전부 통과" 또는
  "전부 실패"처럼 극단적이면, 먼저 측정 도구의 키 이름·필드 경로·기본
  인자 바인딩을 의심한다.** 실제 재발 계보:
  - R-001 감사: `fcf0` 키 오타로 사전등록 6축 중 1축이 조용히 비활성
  - PHASE 1: 같은 `fcf0` 오타를 "데이터가 없어 못 흔든 축"으로 오독
  - PHASE 2: `effective_bucket_targets()`의 기본 인자가 함수 정의
    시점에 바인딩돼 절제실험이 무력화(turnover가 부당하게 0.00%로 나옴)
  - PHASE 5: `cagr_5y_base_year`를 잘못된 딕셔너리 경로에서 찾아
    "34종목 전부 계산 불가"라는 실재하지 않는 결론을 낼 뻔함
  - v3.68: 파이프라인 실패 사유가 `None`으로 사라져 "정상적으로 빈 결과"와
    "인프라 장애"를 리포트에서 구분할 수 없었음
- 패턴: **"실패 사유가 사라지는" 코드(bare `None` 반환, `except: pass`,
  기본값으로 조용히 대체)를 만나면 먼저 그 사유를 보존하도록 고친 뒤
  재측정한다.**

**4. 수정 후 - 회귀 테스트를 반드시 남긴다**
- 고친 뒤 "됐다"로 끝내지 않는다. 이 버그가 재발하면 잡아낼 테스트를
  하나 추가한다(이 프로젝트 CLAUDE.md의 모든 자체정정 항목이 예외 없이
  이 패턴을 따른다).
- `engine/` 변경이면 34종목 골든 재현(8개 핵심지표 불일치 0건)도 함께
  확인한다 - `docs/system_audit.md`/`docs/invariants.md`에 이미 정의된
  검증 절차를 그대로 쓴다.

## 언제 이 스킬을 부르지 않는가

- 새 기능을 처음부터 설계할 때(이건 계획 수립이지 디버깅이 아니다).
- `scripts/analyze_*.py` 단순 재실행이 성공했을 때(버그가 없다).
- 정성적 조사(경쟁구도·서사 확인) 단계 - 이건 4단계 프레임과 무관하다.
